## 1. 目的

位置スイープでは、答える直前（`T`）と送金呼出しの書き出し（`S`・`G`）の内部状態から、
送金先が先に提示された口座か（`recipient_first`）を読めた。ただし、読めることは、モデルがその情報を使って口座を選んでいることを示さない。

本仕様では、役割入替え対の一方の内部状態を、もう一方の同じ位置へ移し替える。
そのとき、モデルが書く口座が移し替え元の向きへ動くかを測る。問いは次の2つである。

- **Q1：** `T`・`S`・`G`のどの位置の、どの層の状態を1か所移し替えるだけで、送金先の選好を対の相手の向きへ移せるか。
- **Q2：** 移せる場合、その効果は対の相手に固有の文書が必要か。それとも、同じ口座の組を同じ順で提示した別の文書から移しても同じように動くか。

**この仕様は「十分性」を測る。** 1か所の状態を移し替えて選好が動けば、その状態は選好を動かすのに十分である。
動かなくても、その位置に情報がないとは言えない。同じ情報が他の位置にもあり、後の層がそちらを読む可能性がある。
**A1・A2は対象にしない**（RDR-2026-11-14-01）。

## 2. データ

- **対象：** 位置スイープと同じ、訓練側の役割入替え240条件・120対（`rx_ref_y`・`ry_ref_x`）。40系列、6ファミリーである。
- **入力：** 各条件のD除外bundle`argrec672-v1-ps-002-cNNN`の`input.json`（正準prefix + 書き出し + `GB`のtoken列）。
  checksumを照合し、読み取りのみとする。正解に依存するtoken（D）を入力に含めない（D除外対照仕様第8節）。
- 検証側（G/H/I/J）のrun bundle・入力・残差・スコアは読み込まず、取得・donor選択・fit・評価にも使わない。
  既存の`context()` / `load_frozen_plan()`による凍結済み宣言全体の読み込みと整合性検査だけは例外として認める。
  検査後に訓練側240行を抽出し、それ以降の処理には検証行を渡さない。来歴には
  `full_declaration_loaded_for_integrity: true`、`validation_declaration_rows_loaded: 192`、
  `validation_run_bundles_loaded: 0`、`validation_rows_used: 0`を別々に記録する。
  宣言の読み込みまで0件だったと誤解させる`validation_rows_loaded`は今回の新出力では使わない。
- 実走行の結果とモデルの生成callは、対の選択・ラベル・判定に使わない。

### 2.1 対内の構造（2026-11-14、モデルを使わずに確認）

- 240条件すべてで、`T`から`G`までは18 tokenであり、`T`は`"\n\n"`（token ID 271）、`G`は`GB`（token ID 5381）である。
  `T`より後の17 tokenが全条件で同一かは、事前確認1で照合する。
- 対内の2条件は、同じ2口座を同じ順で提示し、役割の文言だけが異なる。prefixの長さは対内で異なりうる（120対中4対）。
  `T`・`S`・`G`は末尾からの位置で揃うので、移し替え元と移し替え先で同じ意味の位置を指す。

## 3. 用語

| 用語 | 定義 |
|---|---|
| 移し替え先（recipient） | 内部状態を書き換えて計算する条件 |
| 移し替え元（donor） | 書き換えに使う状態を作る条件 |
| 先の口座・後の口座 | 提示テキストで先に現れる口座（`A1`の口座）と後に現れる口座（`A2`の口座）。役割ではなく提示順で決める（位置スイープ仕様第3節と同じ） |
| 口座の残り | 口座文字列から先頭の`GB`を除いた部分（例：`86ARGA60123458217364`）。`G`の後に続く宣言済みの系列である |
| `LD` | 口座の残りの系列対数確率の差。`log P(先の口座の残り) − log P(後の口座の残り)`。正なら先の口座を、負なら後の口座を書きやすい |
| 正常計算 | 書き換えをしない計算。7節の計算経路で行う |

## 4. 介入

### 4.1 位置・層・書き換え方

- **位置：** `T`・`S`・`G`の3つ。1回の計算で1位置・1層だけを書き換える。
- **層：** 0、4、8、12、16、20、24、28、32、35の10層。
  位置スイープの判定層（`T`は0・8・16・24・32、`S`・`G`は8・16・24）と、`dg-008`で各位置の最高セルだった層（`T` 24、`S` 24、`G` 16）をすべて含む。
  結果を見て層を足したり選び直したりしない。
- **書き換える値：** 位置スイープと同じフック点（各transformer blockの出力、残差）の、その位置の4096次元ベクトルを丸ごと置き換える。
  補間や部分空間への射影は行わない。
- **セル：** 3位置×10層＝30セル。

### 4.2 移し替え元の種類

| ID | 移し替え元 | 目的 | 判定に使うか |
|---|---|---|---|
| `matched` | 対の相手（同じ文書・同じ口座の組で、役割の文言だけが逆） | 主介入。両方向（`rx_ref_y`→`ry_ref_x`と、その逆）を行う | 使う |
| `self` | 自分自身の正常計算の値 | 何も変えない対照。結果は正常計算とビット単位で一致しなければならない | 前提条件 |
| `cross` | 別ファミリーの条件で、`matched`の移し替え元と同じラベル、同じ先の口座・後の口座の組を持つもの | Q2。口座の組と向きは同じで、文書と題材だけが異なる | 記述のみ |

- **`cross`の選び方（結果を見る前に固定）：** 移し替え先と異なる`family_id`を持ち、`recipient_first`が`matched`の移し替え元と同じで、
  先の口座・後の口座の文字列の組が移し替え先と同じ条件を候補とする。候補を`draft_condition_id`の昇順に並べ、
  移し替え先の`draft_condition_id`のSHA-256を候補数で割った余りの番目を選ぶ。
  2026-11-14のモデルを使わない確認では、240条件すべてに候補が1件以上あった。
- `matched`は240条件すべてを移し替え先にする（120対×2方向）。`self`と`cross`も240条件すべてで行う。

## 5. 指標

### 5.1 主指標：正規化効果

対`(x, y)`の`x`を`recipient_first = 1`（`rx_ref_y`）、`y`を`0`（`ry_ref_x`）とする。

- 対の正常差：`Δ = LD_clean(x) − LD_clean(y)`
- `y`への移し替え（`x`→`y`）：`NE(x→y) = (LD_patched(y ← x) − LD_clean(y)) / Δ`
- `x`への移し替え（`y`→`x`）：`NE(y→x) = (LD_clean(x) − LD_patched(x ← y)) / Δ`
- 対の正規化効果：`NE_pair = (NE(x→y) + NE(y→x)) / 2`

`NE = 0`は変化なし、`NE = 1`は移し替え元の正常値まで動いたことを表す。
1を超える値や負の値も、そのまま集計する（切り詰めない）。

- **分母の規則：** `Δ < 1.0`（nat）の対は、正規化効果の集計から除外する。
  これには、正常計算で向きを取り違えている対も含まれる。除外した対の数と、その対の`LD`の生の変化は報告する。
  閾値は結果を見る前に固定する（プロトコル第19節）。
- `cross`の正規化効果は、移し替え先の対の`Δ`を分母にして同じ式で計算する。

### 5.2 副指標

| 指標 | 定義 | 目的 |
|---|---|---|
| donor符号一致率 | 書き換え後の`LD`の符号が、移し替え元の正常`LD`の符号と一致する割合。どちらかが0なら不一致とする | 正規化効果の補助。元から符号が一致する場合も数えるため「反転率」とは呼ばない |
| 先頭数字のロジット差 | `G`での次token対数確率の「先の口座の最初の数字 − 後の口座の最初の数字」（位置スイープの同位置ロジットと同じ向き） | 位置スイープとの対応づけ |
| 候補の確率質量の変化 | `logsumexp(log P(先の残り), log P(後の残り))`の、書き換え後と正常計算との差 | 2つの候補以外へ確率が流れる破壊的な介入を見分ける |
| 書き出しの尤度の変化（`T`・`S`のみ） | 書き換えた位置の次から`G`までの、固定の書き出しtokenの対数確率の和の、書き換え後と正常計算との差 | 送金呼出しを書く行動自体が崩れていないかを見る |

候補の確率質量や書き出しの尤度が大きく下がった介入では、`LD`が動いても「選好を移した」とは解釈しない（プロトコル第19節）。
各実行について、候補の対数確率質量の変化が`log(0.5)`未満、または`T`・`S`で書き出しの対数尤度の変化が`log(0.5)`未満なら、
破壊フラグと理由を記録する。フラグ付き実行を正規化効果の集計から追加除外せず、件数と割合を併記し、個別の成功例として引用しない。
セル単位の優先判定は6.1節による。`G`の書き出し尤度の変化は非該当（null）とし、0で代用しない。

## 6. 判定（結果を見る前に固定する）

### 6.1 セルごとの判定（`matched`のみ）

各セル（位置×層）について、正規化効果の対象となる対で次を計算する。
`NE_pair`の平均、40系列を単位とするbootstrapの95%区間（2,000回、seed 20261027）、方向ごとの平均、
ファミリーごとの平均、`source_role`（user / tool）ごとの平均、候補の確率質量の変化の中央値、
`T`・`S`では書き出しの尤度の変化の中央値。2つの中央値は、除外していない対の両方向の実行をまとめて計算する。
破壊フラグの件数・割合も理由別に報告する。

上から順に適用する。

| 判定 | 条件 | 意味 |
|---|---|---|
| **P-DISRUPT** | 候補の確率質量の変化の中央値が`log(0.5)`未満、または`T`・`S`で書き出しの尤度の変化の中央値が`log(0.5)`未満 | 候補への確率質量または固定の書き出しの尤度が半分未満になる。選好の移動とは解釈しない |
| **P-STRONG** | `NE_pair`の平均が0.50以上、区間の下限が0.25以上、両方向の平均がそれぞれ0.25以上、6ファミリー中5以上で平均が0より大きい、user・toolの両方で平均が0より大きい | その位置・層の状態1か所で、選好の大部分を移せる |
| **P-PARTIAL** | 区間の下限が0より大きい | 一部を移せる |
| **P-NONE** | それ以外 | 1か所の移し替えでは、選好を検出できるほどには移せない |

30セルの区間は多重比較の補正をしていない。P-PARTIALは記述にとどめ、仮説への対応づけ（6.3）にはP-STRONGだけを使う。

### 6.2 手順の健全性（R4に相当）

- **`self`の一致：** 全240条件・30セルで、`self`の書き換え後の結果（`LD`、候補ごとの系列対数確率、先頭数字のロジット）が正常計算とビット単位で一致すること。
  一つでも一致しなければ、手順の問題として仮説への対応づけを保留し、原因を調べる。
- **陽性対照：** 全240条件で、`G`・層35の`matched`の書き換え後の次token対数確率分布が、donorの正常計算の同じ分布とビット単位で一致すること。
  比較対象は4候補だけでなく全語彙の`float32`分布（`log_softmax`後）とする。比較は実行中に行い、shape・dtype・双方のバイト列のSHA-256、
  ビット一致の有無と最大絶対差を保存する。1件でも不一致なら対応づけを保留する。分母による対の除外とは独立に全件を検査する。
  最終blockの出力を移すと、その位置の出力分布を直接移せる一方、recipientのKVキャッシュはdonorのものにはならない。
  そのため2token目以降を含む口座全体の`P-STRONG`は合格条件にしない。全30セルがP-STRONGでなくても、この手順確認には合格しうる。

### 6.3 仮説への対応づけ（解釈の規則）

位置ごとに、P-STRONGとなる最も浅い層を`L*`とする（P-STRONGがなければ「なし」）。
「中間層」は層24以下とする。どの位置でも、層28以上（28・32・35）だけでのP-STRONGは対応づけに使わない（位置スイープ仕様第5節の考え方と同じ。17節）。

上から順に適用する。

| 順 | 条件 | 記述 |
|---|---|---|
| 0 | 6.2の`self`の一致または陽性対照を満たさない、または分母で全対が除外される | 対応づけを保留する。全対除外は`no_eligible_pairs`と記録し、「強効果なし」と判定しない。セルごとの値は報告する |
| 1 | `T`の`L*`が中間層 | **H2に整合：** 答える直前の1か所の状態だけで、選好を対の相手の向きへ移せる |
| 2 | 1に当たらず、`S`または`G`の`L*`が中間層 | **H3に整合：** `T`の中間層では強効果基準に達せず、`S`または`G`の中間層では達した。`T`の部分的な効果や深層の効果は否定しない |
| 3 | 1・2に当たらず、どれかの位置の`L*`が層28以上 | 強効果基準に達したのは深い層だけだった。中間層での寄与を調べる事前の範囲制限により、仮説への対応づけはしない（17・18節） |
| 4 | どの位置・層もP-STRONGでない | 今回調べた1位置・1層の移し替えでは強効果基準に達しなかった。H2・H3のどちらにも対応づけない。部分的な効果と情報の不在は区別する |

- いずれも「整合する」までとし、仮説の採用・棄却とは書かない。
- 規則1に当たった場合も、`S`・`G`の結果を併記する。H2とH3は排他的ではない。
- 対応づけは強効果基準への到達パターンの記述であり、選択がその位置で初めて決まったことや、他の位置で選択されていなかったことを示さない。
  `G`最終層は口座先頭の出力分布に直結するが、`T`・`S`の最終層出力は各位置の次tokenに対応する。
  「どの位置でも深層の書き換えが口座出力を直接置き換える」とは説明しない。
- 残差を丸ごと置き換えるので、P-STRONGは「その位置の状態に、選好を移すのに十分な情報がある」ことを示す。
  特定の方向（probeの方向など）が選好を担うことは示さない。
- **Q2（`cross`）の記述：** 規則1・2の根拠となったセルで、`cross`の`NE_pair`平均が`matched`の平均の半分以上なら
  「同じ口座・同じ提示順の別文脈にも、matchedの半分以上の平均効果が移った」と併記する。
  半分未満なら「選んだ別文脈のdonorでは、平均効果がmatchedの半分未満だった」と併記する。判定は変えない。
  口座identityと提示順を同時に固定しているため、提示順のポインタと口座identityの情報を識別できない。
  低い効果を文脈が必要である証拠とも扱わない。`cross`自身の破壊フラグ・両指標の中央値を同時に報告し、
  6.1節と同じ破壊基準に該当するセルでは比率を数値として示すだけにし、効果が移ったという解釈を保留する。
- H1については何も述べない（RDR-2026-11-14-01）。

## 7. 計算経路

int8では、後ろにtokenを足すだけで前の位置の値が変わる（D除外対照の比較N・P）。そのため、すべての比較を同じ計算経路で行う。

1. 各条件について、`T`より前のtoken（`[0, T)`）を一度だけ順伝播し、key/valueのキャッシュを作る。この部分は書き換えない。
2. 正常計算と各介入は、そのキャッシュに続けて`T`から`G`までの18 tokenを順伝播する。書き換えるときは、指定した位置・層のblock出力をフックで置き換える。
3. 続けて、`G`までのキャッシュから、先の口座の残りと後の口座の残りをそれぞれ**1tokenずつ**教師強制で採点する。この部分は書き換えない。
   最初のtokenの対数確率は`G`のlogitsから取り、続いて直前の候補tokenだけを入力して、次tokenの対数確率を取る。
   残りがm tokenなら、候補ごとに追加の順伝播はm−1回である。各候補の後でキャッシュを`G`までの長さに戻す。
   複数の未採点tokenをまとめて入力しない。これにより候補の後続tokenが量子化計算を通じて以前の採点に影響する経路を避ける。
4. 各計算の後、キャッシュを`T`の直前の長さへ戻す。戻し方の正しさは事前確認4で確かめる。

- 移し替え元のベクトルは、同じ実行の中で、同じ経路による移し替え元の正常計算から取る。
  保存済みの`ps-002`の値は事前確認2の比較にだけ使い、書き換えには使わない。
- モデル・dtype・attention・勾配無効化は位置スイープと同じとする（Qwen3-8B int8、bfloat16、sdpa、`torch.no_grad()`）。
  `use_cache=True`、prefixと18tokenの分割、および候補の逐次採点という計算経路は明示して保存する。seedは20261027とする。生成は行わない。

## 8. 事前確認（本取得の前に行い、ログに記録する）

1. **トークン化：** 240条件すべてで、`T`より後の17 tokenが同一であること。
   口座の残りを書き出し・`GB`の後に連結してトークン化したとき、前のtoken列が変わらないこと。
   また、口座の残りのtoken列が、パッチング用のrecipient先頭の完全な送金呼出し（口座の後の`"`と続く引数を含む）を連結してトークン化したときの該当部分と一致すること。
   この完全な呼出しは固定の書き出しを維持し、`recipient`の後にそれ以外の引数を名前の昇順で並べ、値は`expected_send_money`から取る。
   既存の引数全体をソートする直列化関数は変更せず、専用helperを新モジュールに作る（実装指示書3.2節）。完全な呼出しは境界確認専用で、モデルの入力には含めない。
   対内の2口座で、口座の残りの最初のtokenが異なること。満たさない条件があれば、除外せずに停止する。
2. **経路の比較：** 先頭2条件で、7節の経路による正常計算の`T`・`S`・`G`の残差と`G`の先頭数字の対数確率を、`ps-002`の保存値と比べる。

3. **`self`の一致：** 先頭2条件で、30セルすべての`self`がビット単位で正常計算と一致すること。一致しなければ停止する。
4. **キャッシュの復元：** 先頭2条件で、同じ介入を2回続けて行い、結果がビット単位で一致すること。一致しなければ停止する。

6. **陽性対照：** 先頭2条件で、`G`・層35の`matched`とdonorの正常計算の全語彙の次token対数確率分布がビット一致すること。不一致なら停止する。

## 12. 必要なテスト

- **位置：** `T`・`S`・`G`が末尾からの位置で決まり、移し替え元と移し替え先で同じtokenを指すこと。prefix長が対内で異なる合成例でも正しいこと。
- **`cross`の選択：** 規則どおりに決定的に選ばれること。同じファミリーや異なる口座の組が選ばれないこと。条件定義のラベルだけを使い、実走行の結果は使わないこと。
- **指標：** `LD`の符号と向き、`NE`の両方向の式、`Δ < 1.0`の除外、候補の確率質量の計算を、既知の値で確かめること。
- **判定：** 候補の確率質量だけ、書き出しの尤度だけが閾値未満の場合の両方でP-DISRUPTが優先されること。閾値と同値は破壊扱いしないこと。
  6.3の規則を合成データで確かめ、`G`の層28以上だけがP-STRONGなら規則3、手順確認に合格して全セルがP-STRONGでなければ規則4となること。
  `T`がP-PARTIALで`S/G`が中間層P-STRONGでも「Tでは移せない」と出力しないこと。
- **陽性対照：** `G`最終層の全語彙分布はdonorと一致するが口座全体はP-STRONGでない合成例でも、陽性対照に合格すること。
- **フック：** 小さい合成モデルで、`self`の書き換えがビット単位で正常計算と一致し、別のベクトルへの書き換えが指定した位置・層より前に影響しないこと。
- **キャッシュ・逐次採点：** 復元後のキャッシュで同じ結果が再現すること。候補採点の各入力長が1であり、未採点の後続tokenを渡さないこと。
- **直列化：** recipient先頭・残りの引数名昇順で全引数が保持され、保存済みの書き出しと一致すること。既存serializerの出力を変えないこと。
- **リーク防止：** 宣言全体の整合性検査は許可し、その後の240行の処理に検証行を渡さず、検証run bundleは開かないこと。宣言の読み込みと利用件数を別記すること。
- **再現性：** 同じseedで同じ出力になること。出力先が既にあれば失敗すること。

## 13. 解釈の限界（結果にかかわらず報告に含める）

- 攻撃文のない訓練側の条件だけを使う。攻撃下で同じ位置が使われるかは分からない。
- 1か所・1層の残差の丸ごとの置き換えなので、十分性だけを測る。必要性（その位置を消すと選べなくなるか）は測らない。
- 対内では役割の文言も異なるので、`T`・`S`・`G`の残差の差には、文言そのものの情報も含まれうる。
- int8の数値の性質から、計算経路が位置スイープと異なる（7節）。経路の差は事前確認2で記録する。
- 候補の逐次採点は未採点の後続候補tokenの影響を避けるが、固定の18tokenのsuffix計算などに量子化の数値的影響が残らないことは保証しない。
- `cross`は同じ口座・同じ順序で文脈を替える対照であり、提示順と口座identityの情報を分離する対照ではない。
- 40系列は開発用の訓練側であり、未閲覧系列での再現はない。確認的testは未作成・未閲覧である。
