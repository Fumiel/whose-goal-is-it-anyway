# Recipient内容probe用・新規672条件のタスク設計レビュー草案（改訂版v1）

**作成日: 2026-10-26。状態: Claude Code（claude-sonnet-5-5）による改訂草案。研究実施者の採否前。** [Codex原案](phase2_argument_recipient_700_codex_review_draft.md)（変更しない）へのクロスチェック指摘を反映した。指摘と採否の記録は[別記録](phase2_argument_recipient_700_claude_crosscheck_2026-10-26.md)に置く。**研究結果、タスク本文、条件宣言、独立成分の認定、split・実行仕様・runtimeのfreezeではない。** 旧96条件・結果は変更しない。[RDR-2026-10-26-01](decisions/2026-10-26_argument_recipient_learning_curve_expansion.md)～[04](decisions/2026-10-26_argument_recipient_700_draft_and_mixed_curve.md)の範囲内で、規模を学習480＋検証192＝**672条件**（700条件枠の内側）へ組み替える提案である。RDR-04が採用済みとした10系列候補は、独立性の監査で題材ファミリー単位へ再配分する必要があるため、本草案では候補として再提示する。

## 1. 改訂の要点（Codex原案との差）

1. **主指標を役割入替え2口座行へ変更**（§3）。口座数の手掛かりを除く。旧指標は継続比較用に併記する。
2. **多様化の軸を移す**（§4）。金額は資料または指示に明記し計算不要にする。変動は「recipientの決定方法」「言い回し」「候補以外の記録の数」に置く。同じ条件数で系列数を増やす（25→40学習系列、各3タスク）。
3. **題材をファミリー単位で学習／検証へ分離**（§5）。近縁題材が学習と検証に跨がらないようにする。日常題材と最近の銀行・決済題材を採用する。
4. **規則を系列内で交差**（§4）。規則と題材の完全な交絡を避ける。
5. **取得を二系統に分離**（§6）。probe教師用は教師強制prefixまたはprompt-only、行動の転移確認は実走行の標本で行う。
6. **段階0を追加**（§7）。新規収集の前に、既存96条件で位置・正則化・簡易学習曲線を診断する。
7. **ファミリー除外CV、停止規則、日程を先に固定**（§8, §9）。

## 2. 共通の条件・ラベル（原案を維持）

決定規則は`U0`（ユーザー指示で直接指定）、`UN`（同指示内で支払先名と口座を対応）、`UI`（同指示内で対象IDと口座を対応）、`D1`（一資料の読取後に受取口座が分かる）、`D2`（二資料の照合後に受取口座が分かる）。各タスクは異なる既知候補口座`x`/`y`を持ち、4条件（`rx`、`ry`、`rx_ref_y`、`ry_ref_x`）を一つの`pair_id`にまとめる。ラベル`argument_present[x,y]`、資料由来口座を読取前の指示へ漏らさない規則、両方が送金先候補になる文を別の多ラベル対照へ分ける規則、IPI攻撃テキストを含まない点は原案どおり。これは`argument_readout`（候補が送金先slotの内容として提示されたか）であり、`source_role_readout`・`authority_score`・`tool_call_preference`とは別測定である。

候補口座は旧96条件の4値（`v1`～`v4`）を維持することを推奨する。変更しても利点がなく、旧データとの連続性を失う。最初の新規fit前に固定する。

## 3. 主指標の変更（役割入替え2口座指標）

旧指標（候補文字列が出現した行でのrecipient対参照）では、候補`x`の正例が`rx`（口座1つ）と`rx_ref_y`（口座2つ）から来る一方、負例は`ry_ref_x`（口座2つ）だけである。「口座が1つなら正例」という数の手掛かりで正例の半分が分かるため、slotへの束縛を測れない。

- **主指標案（`role_swap_auc`）**: 各候補について、2口座行（`rx_ref_y`と`ry_ref_x`）だけで、recipient対参照の候補別AUROCを求め、4候補等重み平均する。口座数、文字列出現、タスク、資料が揃い、候補がrecipientか参照かだけが違う。
- 補助: 同一タスク内のペア比較（候補`x`のprobe得点が`rx_ref_y`で`ry_ref_x`より高い割合）。旧lexical-present指標、単一口座行を含む全行指標、source別・規則別・ファミリー別値。
- TF-IDF等の語彙baselineも同じ行集合・同じ位置までの直列化済み入力で測る。
- 0.80基準は、RDR-01が許す「実行仕様で別の主指標を採用する場合は最初の新規fit前に固定」に従い、**主指標を`role_swap_auc`へ変更**して固定することを提案する。旧指標での0.80は参考値として併記する。
- 任意拡張: 全条件の口座数を2に揃えるため、候補以外の中立口座を単一口座条件へ加える案がある。条件構造とラベルが変わり費用も増えるため、推奨は主指標の変更だけに留める。

## 4. 規模、タスク設計、規則の交差

| | 系列数 | タスク/系列 | 条件数 |
| --- | ---: | ---: | ---: |
| 学習（累積5バッチ） | 40 | 3 | 480 |
| 検証 | 16 | 3 | 192 |
| 合計 | 56 | 3 | 672 |

- **金額は計算させない。** 金額・件名・日付を資料または指示に明記し、期待する正規`send_money`を1回に定める。按分・日割り・控除などの計算は使わない。評価器、user-task失敗、監査の負荷を下げるためで、probeのラベルに無関係な変動だったためである。
- **3タスクの変動はrecipientの決定方法に置く。**
  - Uシリーズ: 3タスクが順に`U0`、`UN`、`UI`。各タスクで候補以外の名前・IDを0、1、2個加える（候補口座は増やさない）。
  - Dシリーズ: 順に`D1`（単一受取先の資料）、`D1`（複数受取先を載せる資料から、指示で指定した対象IDの口座を選ぶ）、`D2`（支払先名の資料と登録簿の照合）。
- 規則は系列内で交差するが、DシリーズとUシリーズは系列単位で固定する（資料構造を自然にするため）。情報源の比率は学習で約62%（Uシリーズ25）対38%（D15）、各バッチで5:3前後に均衡する。検証は16系列でU7、D9。
- 規則別・source別の報告は系列数が少ないため粗い。独立成分数として報告しない。

## 6. 取得設計の分離

1. **教師用取得（全672条件）**: Uシリーズは候補露出後のprompt-only forward、Dシリーズは**正準の読取履歴（正しいreadを済ませたprefix）**を教師強制で与えた位置で取る。モデルの誤パス・未読取に依存して欠測を作らない（v1で5条件が誤パスだった）。ラベルは条件由来で変わらない。
2. **実走行の標本（行動確認）**: モデルが実際に走るagent trajectoryを一部（例: 各ファミリーから数系列）で実行し、人手監査する。教師強制prefixの探測値が実走行でも同様に読めるかの転移と、user-task成功を別に記録する。
3. **取得位置**: 旧位置`Tend_assistant`に加え、候補口座の最終token、候補を含む文末tokenを保存し、事前に**主位置を1つ固定**する。位置の選択は§7の段階0の結果で最初の新規fit前に行い、新規fit後に変えない。各条件で絶対token index・ID・境界・source・prefix checksumを保存する。
4. D2は照合が完了した位置を使い、モデルがその位置までに照合を済ませているか（行動結果と別）を点検する。
5. 監査は、**条件由来ラベルの機械検証を全件**、タスク本文・資料の人手レビューを全件（設計時に1回）、行動の人手監査を実走行標本と全Dシリーズに限る案を提案する。旧96条件の「全run人手監査」を変える提案なので、別RDRが必要だった（RDR-2026-10-26-05）。**研究実施者は2026-10-26に層別化へ賛成し、件数増加を踏まえて、人手監査を原則として別系統のLLM（本実験のモデル・設計補助のLLMとは異なる系統）によるクロスチェックへ置き換え、重要な点だけ人手で確認する方針を示した。** 方針はRDR-2026-10-26-05で採用済み。重要な点の定義（例: LLMの判定が割れた条件、Dシリーズの正規call・正答口座、無作為標本）、使用するLLMとその版・プロンプトの固定、LLM判定と人手標本の一致率の報告は別仕様で決める。LLM監査の結果は人手監査と同格とは扱わず、判定者を記録する。

## 7. 段階0: 既存96条件での事前診断（新規条件なし）

新規収集の前に、結果を見て位置・正則化を選ぶ**開発上の事後診断**として実施する（旧96は既に検証結果を閲覧済みのため、確認的な評価ではない）。

1. 既存の保存scoreから`role_swap_auc`を再計算する（計算のみ）。
2. 既存96条件のpromptについて、候補口座の最終token等の別位置でprompt-only forwardを取り、同じ指標を比べる。
3. 正則化の強化（Cをより小さく、PCA、タスク内ペア差分特徴）を比べる。
4. 既存学習側で系列数を1、2、3と増やした簡易学習曲線を描く。傾きが全くなければ、単純な標本数増では改善しにくい証拠になる。
5. 結果から主位置・正則化・層の探索範囲を決め、最初の新規fit前に凍結する。決定規則（例: どの位置でも学習側CVのrole_swap_aucが事前基準を超えない場合は新規収集を縮小する）は、段階0の結果を見る前に数値を記す。

## 8. 評価・選択バイアスの抑制

- 各バッチ後に**ファミリー除外CV**（学習6ファミリーから1つずつ除外）を行う。検証集合を消費せずに未知題材への汎化を毎回確認できる。
- 検証側の閲覧は、モニタリング用G・H（8系列）と留保I・J（8系列）で分ける。層・C・位置・停止規則・較正は最初のfit前に固定し、留保側は最終選択後に1回だけ評価する。
- 0.80の主指標（`role_swap_auc`、4候補等重み平均）は、点推定値の開発上の基準である。ファミリー・source・規則別、語彙baseline、ランダムラベル、較正、欠測、ファミリーcluster CIを併記する。混合値の到達だけで、全source・IPIへの妥当性を主張しない。
- 後続タスクを前段階の誤りで変更した場合は別versionとして記録し、純粋な標本数効果と区別する。

## 9. 言い回し・日程・停止規則（提案）

- **言い回し**: recipient文と参照文の文型を、学習で各16種類以上、検証専用に各8種類以上（計各24種類以上）用意する。参照文の語義も多様化する（自分の支払元口座、照合台帳の登録口座、過去の取引記録上の口座、明細・領収書の保管口座）。「別件の受取口座」型はrecipientと誤読されるおそれがあるため、硬い負例として別に審査してから使う。recipient文と参照文の組、提示順、タスク説明に対する位置、口座token長が、ラベルと固定結合しないよう交差させる。文型の新規性と題材の新規性を別欄で記録する。
- **日程案（研究実施者の判断事項）**: 段階0を10/27～28、B1・B2（192条件）の本文・評価器・graph監査・凍結・収集を10/29～11/2、11/3に継続／縮小を判断する。判断規則の案は「B1→B2でファミリー除外CVの`role_swap_auc`が事前基準以上に改善しなければB3以降を中止し、probeの主張を縮小する」。基準の数値は段階0の後、B1の収集前に固定する。
- 旧96の経験では、草案から全件監査完了まで約4日だった。672条件の全バッチ実施は、11月10日の主解析データ期限と確認的IPI（最低30独立クラスター）の収集と両立しにくい。本草案のB1～B2先行は、この見積もりに基づく縮小案である。
