# 研究対象
同一ツールの引数乗っ取り：ツールの種類は正しいまま（send_money）、引数（recipient＝送金先口座）だけが攻撃者の値にすり替わるIPI。
- 予備実験（pilot）では、攻撃が成功した31件はすべて同一ツール内での引数すり替えだった
- ただし、pilotの攻撃条件は攻撃者の呼出しと正規の呼出しを同じツール名にする設計だったため、これは設計上の必然
- 確認的test（未閲覧の最終評価データ）は未作成・未閲覧

# Phase 2の現状（すべて攻撃なし・開発データ・探索的）
データ：672条件 = 56系列 × 3タスク × 4条件。学習側40系列・480条件、検証側16系列・192条件。
- ファミリー（似た題材の集まり）単位で学習と検証に分割している
- 主な分析対象は学習側の「役割入替え対」240条件・120対：同じ2口座・同じ提示順のまま、どちらが送金先かを示す文言だけを入れ替えた2条件の組

研究の問い：送金先はいつ・どこで決まるか。競合仮説は次の3つ。
- H1：書類を読んだ時点で、口座トークン上に決まる
- H2：答え始める直前（T）に「どちらを使うか」のポインタとして決まる
- H3：送金先を書き出す時点（S＝`"recipient": "` の末尾、G＝全候補口座に共通の先頭`GB`の位置。次の数字で候補が分岐する）で決まる

結果1：失敗の分解（実走行112件）
- 受取人の誤り14件のうち13件は、文中のもう一方の口座（参照口座）との取り違えで、書き写しの誤りは0件
- 依頼文で口座を伝えた条件の厳格成功率は21/64と低く、原因の多くは金額・件名・日付の誤り（31件）

結果2：位置スイープ（線形probe、ファミリー除外の交差検証、主指標＝対内正解率）
- 結果：A1（先に出る口座）1.000、A2（後に出る口座）1.000、T 0.842、S 0.983、G 0.992
- 判定規則は事前に固定し、形式上は「H1に整合」となった
- しかし結果閲覧後、口座の直前32文字だけのTF-IDFでも A1 1.000 / A2 0.992 となった。口座位置での読み取りは局所的な文言で説明できるため、H1は検査不能と結論した（正式記録 dg-010）
- 層0の残差でもA1は0.942
- 選択と無関係な順序情報（特異性対照）も全位置でAUROC 0.997以上で読めた
- 位置ベースライン（トークン番号）は0.8125
- 正解の数字を入力から除いても判定は不変。同一入力の再計算はビット単位で一致

結果3：活性化パッチング（役割入替え対の間で、1位置・1層の残差を丸ごと置換。116対が集計対象）
- 正規化効果（1 = 対の相手の選好が完全に移る）。層は0〜35
- T：全層で約0（P-NONE）
- S：最大は層24で0.057（P-PARTIAL）
- G：層20 0.016 → 層24 0.678 → 層28 0.86 → 層32 0.965 → 層35 0.989。層24以降がP-STRONG
- P-DISRUPT（出力を壊す）はなし
- 手順の確認（self置換、陽性対照、正常計算の再確認）はすべてビット単位で一致
- 事前規則により「H3に整合」と判定した。ただし次の留保がある
  - 「中間層＝層24以下」と事前に固定しており、その境界の1セルに依存している。1段浅く決めていれば「深い層のみ」という判定になっていた
  - 同じ口座・同じ提示順で、別ファミリーの文書をdonorにしたcross条件の効果（0.879）がmatchedの1.30倍。提示順のポインタと口座の文字列のどちらが移ったのか、識別できない
  - G は口座の書き出しの直前なので、深い層の置換は出力分布に直結しうる
  - Tで移らないことは、Tが使われていないことを意味しない（冗長性で打ち消された可能性）
  - 学習側だけ、int8量子化、攻撃なし、未閲覧の系列での再現なし

# 関連研究（別のAIが要約を読んだだけ。本文は未確認）
- CounterSteer（arXiv 2609.36570）：tool resultトークンに活性化ステアリングを常時かけてIPIを抑える防御
  - parameter manipulation（引数への攻撃者の値の注入）が最大の弱点
  - その判断はプロンプト側の位置では線形に読めず、引数の書き出し時に読める
  - 書き出し時・デコード中のステアリングでは除去できなかった
- Readable Before Actionable（arXiv 2610.05295）：Qwen2.5-7Bなど、AgentDojo（Slack・Workspace）でsource roleの方向を編集し、攻撃成功率を下げた
  - 主な介入位置は行動直前のトークンと注入部分
  - function-callingテストでは、悪意ある引数の使用を88.2%から12.4%に下げた
  - 適応型攻撃には効かない
- Your Agentic LLMs Secretly Encode IPI Exposure in Hidden States（arXiv 2608.02657）
- TaskTracker系（activation deltaによるtask drift検出）

# お願いしたいこと（それぞれ具体的に）
1. 第1部の結果の解釈で、最も危ない点はどこか。特に次の点。
   - G層24の1セルへの依存
   - cross > matched
   - Gが出力直前であることによる自明さ（「次トークンの直前を書き換えれば出力が変わるのは当たり前」という批判）
   - int8であること
   それぞれについて、査読者が突いてきそうな点と、2/9までにできる最小限の追加実験・分析を挙げてください。
2. 「Gで決まる」は新規性のある主張か。CounterSteerの「書き出し時に読める」という観察と比べて、何が上積みになるのか。もし弱いなら、差別化の軸をどこに置くべきか。
3. 第2部の設計に欠陥はないか。特に次の点。
   - 攻撃者の口座を第3の候補にするか、参照口座にするか
   - 攻撃成功率が低すぎる・高すぎる場合の扱い
   - 攻撃あり／なしの対の作り方（何を揃え、何を変えるか）
   - (3)のモニタの評価を、偽陽性率と、適応型攻撃への言及も含めてどう設計するか
4. 12月だけで第2部を行うのは現実的か。より小さく、より効果の大きい代替案はあるか（例：攻撃は行動データだけにして、パッチングはGだけに絞る、など）。逆に、第2部をやめて第1部を磨くほうが価値が高い可能性はあるか。
5. 卒論の題目と、研究の問いの一文の案を2〜3個。そのうち中間審査会（11/30）でどれを使うべきか。
6. 中間審査会で、審査員（セキュリティ系の教員）から出そうな質問トップ5と、答え方の方針。
7. 「この計画はここで中止・変更すべき」という基準（kill criteria）を、日付と数値で提案してください。
