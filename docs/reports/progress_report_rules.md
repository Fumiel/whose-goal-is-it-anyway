# 研究進捗報告の作成ルール

## 目的と適用範囲

指導教員へ提出・共有する研究進捗報告は、[共通テンプレート](progress_report_template.md)に従って作成する。過去の報告書には遡及適用しない。報告書単独でも、初めて読む人やAIが研究背景、今回の成果、根拠、限界を理解できるようにする。コード変更履歴ではなく、研究目的、作業の必要性、方法、結果、考察をつなげて記す。

報告書は研究計画や実験手順を変更する文書ではない。研究目的は`docs/research_proposal.md`、実験手順は`docs/experimental_protocol.md`を正本とし、重要な変更は該当するResearch Decision Record（RDR）を参照する。

## 作成前に確認する情報

1. `PROJECT_STATE.md`で、作成時点の作業状況、未解決の判断、確認用データの状態を確認する。
2. 研究目的や仮説に関わる記述について、`docs/research_proposal.md`を確認する。実験方法、結果の分類、解釈に関わる記述について、`docs/experimental_protocol.md`の該当箇所を確認する。
3. `docs/decisions/README.md`と関連RDRの本文を読み、変更の範囲、`status`、`supersedes`、残る制約を確認する。日付や一覧の要約だけで現在の許可範囲を推定しない。
4. 前回の進捗報告書を確認する。前回報告は当時の記録であり、現在の状態の根拠としてそのまま再利用しない。
5. 前回報告時点から情報確認日までのGit差分と、関係する実験結果、監査記録、ログ、設定、README、設計文書を確認する。commitメッセージだけで成果を判断しない。

報告対象期間と情報確認日を分ける。期間内の出来事と、その後に判明した事実を混同せず、後者を含める場合は判明日を記す。情報源が食い違う場合は、差異と確認状況を記す。重要事項の根拠を確認できなければ「要確認」と明記し、成果として断定しない。

## 記述ルール

- 学術的に適切な日本語の「である調」で記す。技術用語は初出時に必要な範囲で定義する。
- 第1章は単独で全体像が分かるように書き、背景の重複は抑える。第3章は前回からの変化に絞る。
- 研究目的、仮説、方法、観測結果、解釈、予定を区別する。仮説や検討中の事項を実施済みの成果として書かない。
- 数値には対象、分母、集計単位、確認方法、出典を添える。条件、試行、タスク系列、独立した分割単位を混同しない。割合や成功率を書くときは、除外・欠測・技術的失敗の扱いも示す。
- 探索的結果、確認的結果、工学的検証、合成fixtureによる確認を区別する。監査前の機械集計を監査済みの結果として書かない。失敗した基準判定を後続作業の進行によって合格扱いしない。
- ユーザータスク成功と攻撃成功を分ける。攻撃なし条件でのタスク失敗、評価器矛盾、失敗runも、研究上の意味があれば報告する。
- `action_readout`、`argument_readout`、`source_role_readout`、`authority_score`、Attention、ツール呼出し選好を別の測定として扱う。読み出しスコアや権限スコアの上昇だけで、目的の採用や因果的な乗っ取りを主張しない。
- コード変更と研究上の成果を混同しない。単純なリファクタリングは簡潔に扱い、測定・評価・再現性に影響する設計変更を説明する。
- 重要な研究判断や実験条件の変更には、変更前後、理由、判断日、結果を確認した範囲、関連RDRを示す。検討中の変更は決定と区別する。
- 図表には対象、単位、分母、集計方法、出典を付ける。本文の結論が図表と参照先から支持されるか確認する。
- 確証のない原因は仮説と明示する。結果から判断できないことや代替説明も記す。

## 詳細度と参照

文章量の削減を最優先しない。初読者に必要な研究背景、結果を解釈するための条件、重要な限界を残す。一方、前回から不変の説明、重複、研究上重要でない実装詳細は抑える。必要な証拠を本文の近くで示し、詳しい設定、run ID、コマンド、checksumは第8章へ整理する。リポジトリ内の参照は相対リンクを用い、外部資料は資料名・版・確認日が分かる形で記す。

## 出力と確認

1. `docs/reports/progress_report_template.md`を複製し、`docs/reports/進捗報告_［氏名］_YYYYMMDD.md`としてMarkdown原稿を作る。角括弧内の記入案内、HTMLコメント、不要な例をすべて削除または置換する。該当事項がない欄は、必要に応じて「該当なし」と理由を記す。
2. 提出用DOCXを同じ原稿から同名で生成し、見出し階層、表、余白、図表、改ページ、リンクを目視で確認する。
3. MarkdownとDOCXで、数値、結論、注記、参照先を一致させる。媒体固有のページ番号や図表番号を除き、内容を変えない。
4. 提出前に、日付とGit範囲、数値の分母、根拠の状態、未解決課題、変更判断、参照先を再確認する。
