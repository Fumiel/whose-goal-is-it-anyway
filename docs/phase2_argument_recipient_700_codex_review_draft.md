# Recipient内容probe用・新規700条件のタスク設計レビュー草案

**作成者: Codex。作成日: 2026-10-26。状態: Claudeによるクロスチェック前のレビュー草案。**

この文書は[RDR-2026-10-26-01](decisions/2026-10-26_argument_recipient_learning_curve_expansion.md)～[04](decisions/2026-10-26_argument_recipient_700_draft_and_mixed_curve.md)で採用された計画・方針を、35系列候補と各5タスクの概念へ展開する。**研究結果、175タスクの完成本文、700条件の宣言、独立成分の認定、split・実行仕様・runtimeのfreezeではない。** Claudeの指摘を受けた修正は日付、理由、研究実施者の採否を別記録へ残す。旧96条件・結果は変更しない。

## 1. 採用済みの範囲と今回Codexが提案する範囲

- 研究実施者が採用済み: 新規の学習25意味系列×各5タスク×各4条件＝最大500条件、検証10系列×各5タスク×各4条件＝200条件。学習は5系列・100条件ごとにfitし、未知系列AUROC 0.80以上を開発上の到達基準にする。5種類のrecipient決定規則、4条件の口座役割入替え、複数の文型と交差、資料由来条件を同じ混合学習曲線へ含める方針も採用済み。
- 研究実施者が**系列候補**として採用済み: 下表のT01～T05、V01～V05の10テーマと前回提示した各5タスク概念。候補を独立groupや最終splitとして採用したわけではない。
- **今回Codexが新たに提案し、Claudeクロスチェック待ち**: T06～T25、V06～V10の25テーマ、各行の情報源・決定規則の暫定割当、5タスクへの具体化、5バッチの順序と検証候補の近縁性に関する仮説。研究実施者の採否と関係graph監査が必要。

ここでのT/Vはレビュー用IDであり、安定した`condition_id`、`task_template_id`、`component_id`ではない。Vは**検証候補**を示すだけで、学習系列・旧pilot・旧96条件から独立しているという主張ではない。35系列候補を700件に機械的に展開しても、関係graphで10個の独立検証成分を確保できるとは限らない。

## 2. 共通の条件・ラベル・観測規則

決定規則IDは`U0`＝ユーザー指示で直接指定、`UN`＝同指示内で支払先名と口座を対応、`UI`＝同指示内で対象IDと口座を対応、`D1`＝一資料の読取後に受取口座が分かる、`D2`＝二資料の照合後に受取口座が分かる、を表す。各系列に表中の主規則を一つ置き、5タスクで対象・計算・選択・照合を変える。規則の種類は意味系列の独立性を保証しない。D1/D2の正規資料は通常のタスクデータであり、この700条件はIPIの攻撃テキストを含まない。

各タスクに異なる既知候補口座`x`/`y`を割り当て、次の4条件を一つの`pair_id`へまとめる。正例は**生成された送金先**ではなく、指定位置までに`send_money.recipient`の内容として提示された候補である。

| variant | 送金先として提示 | 別用途の参照口座 | `argument_present[x,y]` |
| --- | --- | --- | --- |
| `rx` | `x` | なし | `[1,0]` |
| `ry` | `y` | なし | `[0,1]` |
| `rx_ref_y` | `x` | `y` | `[1,0]` |
| `ry_ref_x` | `y` | `x` | `[0,1]` |

4条件では同じタスク対象、金額決定規則、資料構造、必要な読取・正規操作を保つ。`D1`ではrecipientと参照口座を同じ読取資料の異なる役割欄へ置き、`D2`では支払先名・対象IDを示す一資料と口座対応を示す登録簿を照合し、二口座提示時は登録簿内にrecipientと別用途欄を置く。`U0`/`UN`/`UI`では必要な口座内容をユーザー指示内に置く。資料由来の口座値を読取前のユーザー指示へ漏らさない。両方が送金先候補になる文はこの4条件へ入れず、多ラベル対照へ分ける。

送金先の誤りと金額等の失敗は別に採点する。各タスクは原則として正規の`send_money`を1回要求し、余分な状態変更を許さない。資料読取の要否、期待recipient・amount・subject・date、独立した`user_task_success`と`attack_success`、baseline failureを実行仕様で定める。候補口座の実値、資料本文、数値、具体的英文、native tool受入はまだ未検証である。

## 5. 言い回し・候補値・バッチの均衡

依頼文、説明文、欄形式、手順文、文中埋め込み、表形式を素材とし、recipient側と参照側の文型を固定ペアにしない。同じ候補値がrecipientにも参照にも現れ、二文の提示順、タスク説明前後の配置、口座値のtoken長が特定ラベルに固定されないようにする。各バッチの5系列に`U0`/`UN`/`UI`/`D1`/`D2`を一つずつ置き、検証10系列にも各規則を二つずつ暫定配分する。文型の既知性と未知性、規則の新規性、意味系列の新規性を別欄で記録する。

候補口座は既知の4値を第一案とするが、旧96条件の4文字列をそのまま再利用するか、新たな4値にするかは未決定である。値が変われば旧probeとの連続比較の意味も変わるため、最初の新規fit前に固定する。4候補の正例・参照負例を系列とバッチでほぼ均衡させる。5タスク×4条件では一系列内の完全均等は保証できないため、候補別件数をバッチと検証全体で確認する。各条件の文・資料・口座位置は生成後に機械的な偏り検査と研究者レビューを受ける。

## 6. 混合学習曲線と評価

1. 新規100、200、300、400、500条件の**累積**学習集合を作る。各段階の対象は完全な5系列・25タスク・100条件であり、停止で未収集の系列は実行済みと数えない。各バッチの源・決定規則の構成を一定にする。後続タスクを前段階の誤りで変更した場合は別version・日時・理由を記録し、純粋な標本数効果と区別する。
2. `U0`/`UN`/`UI`は候補がユーザー指示へ露出した後、`D1`は該当資料読取後、`D2`は二資料が揃った後の事前指定位置で残差を取る。同じ位置選択規則を全段階に適用し、絶対token index、ID、境界、source、prefix checksumを保存する。読取未接触、順序違い、空資料、token不整合は理由別に欠測として保持する。行動成功だけを包含条件にしない。
3. 現行実装の「候補がユーザー指示にあるか」の確認を、選択位置までの**実際の直列化済み入力**に拡張する。TF-IDF等の語彙baselineも同位置までに見えた内容を用い、文字列出現だけの判定とrecipient対参照の判定を分ける。train-only標準化・前処理、候補別線形probe、random-label controlと較正・欠測診断を維持する。境界混合の特徴分布差を記録し、source別・規則別・系列別AUROCも報告する。
4. 主到達基準の候補は、従前と同じ「候補文字列が選択位置までに出現した行でのrecipient対参照」候補別AUROCの四候補等重み平均が**未知系列で0.80以上**であること。これは開発用の点推定値基準である。10検証系列のうち反復モニタリングに使う系列と最終まで留保する系列、層・C・閾値・較正・停止規則を最初のfit前に固定する。混合値が達してもsource別の低成績、語彙baseline、ランダムラベル、欠測、信頼区間、IPI対応対照を別に確認する。

## 7. Claudeクロスチェックで優先して確認する点

1. T01～T25とV01～V10の具体的な正規目的・資料・算出／選択規則に、旧pilot/二文書v2/96条件および系列間の近縁edgeがないか。特にV01↔T22、V02↔V08、V03↔T16/T18、V04↔V09、V05↔V10、V07↔T11/T13を再判定する。
2. 各5タスクが同系列内で意味のある変化を持ち、単なる金額・名前・文面変更になっていないか。逆に、異なる系列名を付けた近縁タスクがあるか。
3. `D1`/`D2`の4条件で参照口座が自然な別用途を持ち、両口座をrecipient候補として提示する曖昧例を生んでいないか。二資料の読取順と全資料露出後の位置が取得可能か。
